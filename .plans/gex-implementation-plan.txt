lines) as a deliberate simplicity choice for a single-feature app. gex
is adding two more substantial features (GEX math + a whole second
charting library) and will likely be worked on by more than one agent

burden risk at that point. Splitting now, before new feature code
exists, is strictly easier than splitting later. This is an explicit
architectural decision for Phase 0 — do it first, as pure mechanical
extraction (move code, adjust imports, no logic changes), verify with
`bun run build` + `bun test` before writing ANY new feature code.

6.3 NEW: OHLC price history for Tab 3 — Yahoo chart endpoint

  Expected response shape (standard, widely used by yfinance and
  others):
    {
      "chart": {
        "result": [{
          "timestamp": [<unix seconds>, ...],
          "indicators": {
            "quote": [{
              "open": [...], "high": [...], "low": [...],
              "close": [...], "volume": [...]
            }]
          }
        }],
        "error": null
      }
    }

  null (Yahoo pads non-trading periods with nulls).

  handleCboe — plain relay, no session needed):

      -> return upstream JSON as-is with permissive CORS headers,
         same as handleCboe's response handling.

  Client side (src/providers/chart.ts): fetch this route, parse into
  OhlcBar[], no crumb logic needed (unlike yahoo.ts).

  On GitHub Pages without a running proxy: Tab 3 requests fail with
  the SAME "needs proxy" messaging pattern the app already uses for
  CBOE/NASDAQ/YAHOO on hosted static deploys — this is consistent
  with existing UX, not a new failure mode to design. See section 14
  for the explicitly-deferred CACHE-embedded-OHLC alternative.

7. GEX MATH SPECIFICATION (exact formulas + decisive tie-break rules)
====================================================================
Convention used: the "SpotGamma-style" public convention (gamma
positive-contribution for calls, negative for puts, using raw open
interest — NOT a customer-buy/sell-classified position). This is the
most common convention across public GEX write-ups and open-source
implementations found during research (spotgamma.com's own
explanation, the open-source repo FlashAlpha-lab/gex-explained, and
an independent calculator at flashalpha.com all describe the same
convention). It is a MODEL APPROXIMATION, not a measured fact — see
section 17 item 3 for the honest caveat on this.

Constants (define as named exports in gex.ts, do not inline magic
numbers):
  const CONTRACT_MULTIPLIER = 100;
  const SECOND_WALL_MIN_DISTANCE_PCT = 0.02;   // see 7.4

7.1 GEX per contract
--------------------------------------------------------------
  gexCall(gamma, openInterest, spot) =
      gamma * openInterest * CONTRACT_MULTIPLIER * spot * spot * 0.01
  gexPut(gamma, openInterest, spot) = -gexCall(...)   // same formula, negated

  If gamma is null for a quote: exclude that contract from the sum
  entirely (do not treat null as 0 silently without this being a
  documented choice — it IS the documented choice). This will
  naturally happen for providers without greeks (e.g. NASDAQ) unless
  enrichQuoteWithModelGreeks has already filled it via Black-Scholes.

7.2 computeGexProfile(quotes, spot) -> GexPoint[]
--------------------------------------------------------------
  Group the given OptionQuote[] by strike (across whatever
  expirations were passed in — caller decides which expirations to
  include, see section 8.1 on the expiration selector). For each
  strike group:
    callGex = sum of gexCall(...) over side === 'call' quotes
    putGex  = sum of gexPut(...) over side === 'put' quotes
    netGex  = callGex + putGex
    callOi/putOi/callVolume/putVolume = straightforward sums
  Return array sorted ascending by strike.

7.3 findGammaFlip(profile) -> number | null
--------------------------------------------------------------
  Exact algorithm (v1 — the "cumulative sum crosses zero" approach;
  the more expensive hypothetical-spot-recompute approach is
  explicitly OUT OF SCOPE for v1, see section 14):
    1. profile already sorted ascending by strike (from 7.2).
    2. Build cumulative[i] = sum(profile[0..i].netGex) for i = 0..n-1.
    3. Find the first i where cumulative[i] and cumulative[i+1] have
       opposite sign (or cumulative[i] === 0 exactly -> flip =
       profile[i].strike, done).
    4. If found: linearly interpolate between profile[i].strike and
       profile[i+1].strike:
         flip = strike[i] + (strike[i+1] - strike[i]) *
                (0 - cumulative[i]) / (cumulative[i+1] - cumulative[i])
    5. If cumulative never changes sign across the whole range
       (all-positive or all-negative gamma exposure in this chain
       slice): return null. Do NOT extrapolate outside the available
       strike range.

7.4 findCallPutWalls(profile) -> { callWall, putWall, callWall2, putWall2 }
--------------------------------------------------------------
  callWall = the strike with the MAXIMUM netGex among strikes where
             netGex > 0. null if no strike has positive netGex.
  putWall  = the strike with the MINIMUM (most negative) netGex among
             strikes where netGex < 0. null if none.
  callWall2 ("Resistance 2") = among strikes with netGex > 0 AND
             |strike - callWall| >= SECOND_WALL_MIN_DISTANCE_PCT * spot,
             the one with the next-highest netGex. null if none qualify.
  putWall2 ("Support 2") = symmetric rule for the put side.
  NOTE: this 2%-of-spot distance rule for "wall 2" is an ORIGINAL,
  UNSOURCED heuristic (no public standard exists for a "second wall")
  — flagged explicitly in section 17 item 6, treat the constant as
  tunable, not sacred.

7.5 computeMaxPain(quotes) -> number | null
--------------------------------------------------------------
  Standard, uncontested formula. For every distinct strike S present
  in the given quotes:
    payout(S) = sum over calls: callOi(K) * max(0, S - K)
              + sum over puts:  putOi(K)  * max(0, K - S)
  maxPain = the strike S (from the same set of distinct strikes) that
  minimizes payout(S). null only if quotes is empty.

7.6 computePCRatio(quotes) -> { byOi, byVolume }
--------------------------------------------------------------
  byOi     = sum(putOi) / sum(callOi)      — null if sum(callOi) === 0
  byVolume = sum(putVolume) / sum(callVolume) — null if denominator 0

7.7 computeGexLevels(quotes, spot) -> GexLevels
--------------------------------------------------------------
  Convenience wrapper: calls computeGexProfile then all of 7.3-7.6,
  assembles the GexLevels object (section 5), plus totalNetGex = sum
  of profile.netGex. THIS is the single function both GexView and
  ChartView call — neither view recomputes anything itself.

7.8 Explicitly NOT implemented in v1
--------------------------------------------------------------
  - HVL / Vol Trigger: proprietary, unsourced heuristics from
    third-party tools with no public formula. Do not implement a
    guessed version. Not in the sidebar, not in Key Levels.
  - The "AG" toggle seen in the reference screenshots: meaning was
    never confirmed from any source. Dropped entirely, not a metric
    toggle option in Tab 2.
  - Gamma Flip approach B (recomputing gamma at a grid of hypothetical
    spot prices via the existing blackScholesGreeks function instead
    of using gamma "as reported at current spot"): a valid future
    enhancement, NOT v1. The function signature findGammaFlip(profile)
    should stay stable so this can be swapped in later without
    touching callers.

8.1 Tab 2 — GexView (see gex-implementation-plan-wireframe-tab2-gex.svg for exact layout)
--------------------------------------------------------------
  Left sidebar (fixed width, matches wireframe proportions — sidebar
  ~300px on desktop widths, stacks above the chart on narrow/mobile
  widths consistent with the app's existing responsive breakpoints):
    - "OI Volume" card: Total Call OI, Total Put OI (plain sums).
    - "GEX Analysis" card: Total Net GEX (formatted, e.g. "+2.14B
      $/1%"), and a plain-language "Regime" label: "Positive gamma"
      if totalNetGex > 0, "Negative gamma" if < 0, "Neutral" if
      exactly 0 or spot/quotes missing.
    - "Key Levels" card: Call Wall (R1), Resistance 2 (only if not
      null), Gamma Flip, Put Wall (S1), Support 2 (only if not null),
      Max Pain — each as a labeled price row, using the SAME color
      per level as Tab 3 uses for its price lines (see 8.2) so the
      two tabs are visually consistent: Call Wall/Resistance = green
      family, Put Wall/Support = red family, Gamma Flip = purple,
      Max Pain = amber/yellow.
    - "P/C Ratio" card: By OI, By Volume.
  Above the chart, reusing the EXISTING expiration-chip UI pattern
  from Tab 1 (same component/styling, not reinvented): multi-select
  expiration chips + "All"/"None" toggle. DEFAULT SELECTION for Tab 2
  specifically: nearest single expiration selected by default (not
  "All") — GEX concentrates heavily in near-dated options and an
  "All expirations combined" default view is visually noisy and less
  useful; the user can still pick "All" or other dates manually.
  Also above the chart: metric toggle buttons — Net GEX (default),
  Call OI, Put OI, Call Volume, Put Volume. Selecting one changes
  which GexPoint field the bars plot; Net GEX is signed (calls up/
  green, puts down/red from the zero axis, matching the wireframe);
  the OI/Volume metrics are unsigned (calls and puts as two same-
  direction series, or side-by-side bars — implementer's call on
  exact rendering as long as it's clearly calls-vs-puts).
  Main chart: recharts <BarChart> (already a dependency, do not add a
  new library for this). X axis = strike. A <ReferenceLine> at the
  current spot price (dashed, amber, labeled). <ReferenceLine>s (or
  shaded <ReferenceArea>s) at Call Wall / Put Wall strikes in their
  respective colors, per the wireframe.

17. LIMITATIONS AND ADDITIONAL RESEARCH REQUIRED (read this — honest)
====================================================================
This section lists everything in this plan that is NOT independently,
directly verified, so implementing agents know exactly where to be
careful and what to double-check rather than trusting blindly.

  1. Yahoo chart endpoint (section 6.3): the exact upstream URL,
     "no crumb needed", and response JSON shape are corroborated by
     TWO independent secondary sources found during research, but
     were NOT confirmed with a live HTTP request in this session
     (this environment's fetch tool could not reach query1.finance.
     yahoo.com directly). BEFORE writing providers/chart.ts, do one
     manual request (curl or browser) to
     https://query1.finance.yahoo.com/v8/finance/chart/SPY?interval=1d&range=1mo
     and confirm the field names match section 6.3 exactly, and
     handle the case where `chart.error` is non-null (invalid symbol,
     rate limited, etc. — no error-shape example was captured).

  2. CBOE schema (section 6.1) is HIGH confidence — it was read
     directly out of your own already-working code in three separate
     places (proxy, live provider, Python fetcher), not guessed. The
     only unverified edge case: whether CBOE ever omits gamma/delta
     entirely for very illiquid/far-OTM contracts in a way your
     existing null-handling doesn't already cover. Given the existing
     code already wraps every field in a nullable num() parser, this
     is low risk, but worth a glance at real output for a thin name
     (e.g. a small-cap ticker) if time allows.

  3. The GEX formula convention (section 7, intro) is the most common
     PUBLIC convention, cross-checked across 3 independent sources,
     but it is a MODELING CHOICE, not a verified fact about real
     dealer positioning (the actual buy/sell side of every option
     trade is not public data). It was also NOT reverse-engineered
     against the specific third-party "Max Power" product's actual
     numbers — there was no way to do that (closed product, no API
     access). Do not expect this implementation's numbers to match
     Max Power's exactly; expect them to be in the same ballpark and
     directionally consistent with other public GEX tools.

  4. findGammaFlip's cumulative-sum-crossing-zero algorithm (section
     7.3) is a concrete, defensible, commonly-used definition, but it
     was NOT validated end-to-end against a real live SPY/SPX chain
     compared to a third-party's published gamma-flip number for the
     same moment. Do this sanity check manually once Phase 3 is
     working (fetch a real chain via the live CBOE provider, compute
     levels, eyeball them against any free public GEX site for the
     same ticker/day) — expect "same neighborhood", not an exact
     match, per point 3 above.

  5. The exact required attribution wording for lightweight-charts
     (section 15) is a reasonable paraphrase, not a copy of the
     literal NOTICE file from tradingview/lightweight-charts — that
     file was not fetched in this session. Pull it before Phase 5
     ships.

  6. The "second wall" 2%-of-spot distance rule (section 7.4) has NO
     public source — it does not exist as a standard concept anywhere
     researched. It is this plan's own invented tie-break rule so the
     behavior is at least deterministic and documented. Treat
     SECOND_WALL_MIN_DISTANCE_PCT as a tunable constant to revisit
     once you can see it behave on real strike spacing for the
     tickers you actually care about (SPY's $1 spacing vs. a small-
     cap's $2.50/$5 spacing will behave very differently at a fixed
     2% threshold).

  7. .github/workflows/*.yml in the gex repo were confirmed to exist
     by filename only (ci.yaml, dependency-updates.yml, github-
     pages.yml, update-data.yml) — their actual contents were NOT
     read in this session. Before Phase 0's file-layout refactor
     lands, read ci.yaml specifically to confirm it doesn't hardcode
     any path that the refactor would move (e.g. a lint/build command
     that globs src/main.tsx specifically rather than src/**).

  8. The old options-desk AGENT.md had an explicit "ask the human
     before changing data/options/*.json schema or touching
     workflows" rule (restated here as R3/R4). That file is gone in
     gex and was never replaced with an equivalent for this repo. This
     plan assumes the same caution still applies (the human's own
     message frames this as "starting from scratch" on the AGENTIC
     SETUP specifically, not as license to relax data-safety rules)
     — but this is an assumption, not something the human confirmed
     explicitly for the new repo. If a future task in this repo seems
     to require touching data/options/*.json schema or a workflow
     file, stop and confirm with the human rather than relying on
     this plan's restated rule as authorization.

  9. A CBOE historical daily-bars endpoint was mentioned in earlier
     research as a possible fallback if the Yahoo chart endpoint ever
     breaks, but was never verified with a real URL — it remains an
     unverified hypothesis, not a fallback you can implement today.
     Only chase this down if/when the Yahoo endpoint actually stops
     working.
